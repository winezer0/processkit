# 路径与进程环境变量展开设计方案

## 状态

设计记录。`expand` 提供统一的变量展开，`pathresolver` 和 `processrunner` 调用它；跨平台结果仍需由各平台 CI 验证。

## 目标

- 在 `pathresolver` 中支持路径字符串中的内置目录变量。
- 在 `processrunner` 中支持子进程环境配置值中的相同变量，例如把 `XDG_CONFIG_HOME` 配置为 `${APP_DIR}/third`。
- Windows、Linux、macOS 使用同一套变量语法，并由 Go 标准库返回当前平台对应的目录。
- 允许调用方通过 map 显式传入应用相关变量，例如 `APP_DIR`、`ENGINE_DIR`。
- 默认只解析内置变量和调用方明确提供的变量；可由调用方显式启用环境变量展开，不调用 shell。

## 包职责

建议提供独立的 `expand` 包，作为字符串变量展开的唯一实现。它负责变量语法、内置目录值、调用方 map 合并、名称校验和未知变量错误；不负责路径查找、文件系统检查或启动进程。

- `pathresolver` 在执行现有路径解析前调用 `expand`，覆盖目标路径及所有路径类型的 `Options` 字段。
- `processrunner` 在启动前调用 `expand` 展开可执行文件、参数、工作目录和每个配置环境变量的值。子进程环境变量名本身不展开。
- Tanscan 组合根根据程序和扫描引擎的实际可执行文件路径生成 `APP_DIR`、`ENGINE_DIR` 等上下文值，通过 map 传给调用方 API。当前工作目录不用于推导这些目录。
- `processrunner` 应把“传给子进程的环境值”和“用于模板替换的变量 map”作为不同输入，避免混淆。具体字段名由其 API 设计确定。

## 变量清单

### 内置变量

| 变量 | 值来源 | 说明 |
| --- | --- | --- |
| `${HOME_DIR}` | `os.UserHomeDir()` | 当前运行账号的主目录 |
| `${TEMP_DIR}` | `os.TempDir()` | 当前系统的临时目录 |
| `${USER_CONFIG_DIR}` | `os.UserConfigDir()` | 当前用户的系统配置目录 |
| `${USER_CACHE_DIR}` | `os.UserCacheDir()` | 当前用户的系统缓存目录 |

内置变量由 `expand` 根据运行平台解析，调用方不能通过自定义 map 覆盖。目录 API 返回错误或空值时，解析应返回带变量名的错误，不静默替换为空字符串。

### 调用方变量

其余变量一律由调用方传入，不由 `pathresolver` 根据字段名称推断。例如：

- `APP_DIR`：应用程序目录。
- `ENGINE_DIR`：调用方根据扫描引擎二进制路径计算出的目录。
- `PROCESS_DIR`、`WORKING_DIR`：调用方需要时显式提供的目录。

建议在 `pathresolver.Options` 中增加字段：

```go
type Options struct {
	// Existing path-resolution options...
	Variables map[string]string
	ExpandEnv bool
}
```

map 的键使用不带 `${}` 的大写名称，例如 `"ENGINE_DIR"`；值为调用方明确允许用于路径解析的字符串。这样 map 本身就是调用方提供的变量白名单。内置名称不得重复定义；非法名称、空值和未知变量应返回清晰错误。

`processrunner` 也接收调用方变量 map。Tanscan 的配置例如：

```yaml
environment:
  XDG_CONFIG_HOME: "${APP_DIR}/third"
```

Tanscan 启动时从自身可执行文件位置计算 `APP_DIR`，并通过 map 传入；`${APP_DIR}` 因此不依赖部署版本号、启动目录或机器上的固定绝对路径。`processrunner` 展开环境变量的值后再设置子进程环境。未知变量应在启动子进程前报错。

## 语法与解析规则

- 输入路径始终只使用 `${NAME}` 形式；名称区分大小写，并满足 `[A-Z][A-Z0-9_]*`。启用 `ExpandEnv` 只增加从当前进程环境读取变量的能力，不改变语法。
- 支持一个路径中出现多个变量，例如 `${ENGINE_DIR}/config/katana.yaml`。
- 变量展开在绝对路径判断、候选目录拼接和文件系统检查之前执行。
- 对 `Resolve` 的目标路径，以及 `Options.ProcessDir`、`WorkingDirectory`、`ExecutablePath`、`AdditionalBases[].Path` 等路径字段使用同一套展开规则。
- 对 `processrunner` 收到的可执行文件、参数、工作目录和子进程环境配置值使用同一套展开规则；仅展开环境配置值，不展开键名。
- map 中的值按字面值处理，不递归展开其中的变量标记。调用方需要组合变量时，应先在调用方计算最终目录，再放入 map。
- 默认未知变量、格式错误的变量标记和不可用的内置目录均返回错误；启用环境变量展开时，未设置的环境变量按 `os.ExpandEnv` 语义替换为空字符串。
- 路径字段支持以 `~/` 或 `~\` 开头的相对路径，并展开到当前用户主目录；单独的 `~` 和 `~user` 不展开。其他字符串不处理 `~`。不支持 `%NAME%`、`$NAME` 或 shell 表达式。

展开后仍由现有路径解析流程处理。路径清理和绝对路径判定继续使用 `filepath`，因此分隔符和绝对路径语义遵循当前运行平台。该机制不负责把 Windows 路径转换成 Linux 路径，或反向转换。

## 使用示例

```go
result, err := pathresolver.Resolve(`${ENGINE_DIR}/config/katana.yaml`, pathresolver.Options{
	Kind: pathresolver.KindFile,
	Variables: map[string]string{
		"ENGINE_DIR": filepath.Dir(engineExecutable),
		"APP_DIR":    appDirectory,
	},
})
```

`${HOME_DIR}`、`${TEMP_DIR}`、`${USER_CONFIG_DIR}` 和 `${USER_CACHE_DIR}` 无需放入 map。调用方决定是否提供 `ENGINE_DIR` 等应用变量；未提供时引用这些变量应得到明确的未知变量错误。

## 安全边界

- 默认不读取任意环境变量；启用 `ExpandEnv` 后，仅对 `${NAME}` 表达式读取当前进程环境。内置变量和调用方 map 优先于环境变量。
- 变量展开只生成路径字符串，不执行命令，也不经过 shell。
- 自定义 map 的值具有调用方赋予它的路径或子进程环境权限；调用方应避免把不可信输入直接作为变量值。
- 变量解析不会限制 `..` 越出候选目录。若调用方需要目录沙箱，仍须单独做路径边界校验。
- 展开环境值不等于执行 shell；进程仍通过参数数组和明确构造的环境启动。环境值进入子进程后可能影响其行为，仍由调用方负责配置审查。

## 错误与兼容行为

- 变量展开失败时，`Resolve` 返回错误，不进入候选目录搜索。
- 错误信息应指出变量名和原因，但不包含不必要的环境变量内容。
- 不含 `${...}` 的现有路径保持原有解析行为。
- 当前 `Options` 字段和候选目录优先级保持不变；变量展开仅作为解析前步骤。

## 验收测试建议

- 内置变量分别与对应 `os.UserHomeDir`、`os.TempDir`、`os.UserConfigDir`、`os.UserCacheDir` 的平台结果一致。
- 自定义 map 能解析单变量、多变量、完整路径和路径片段，并保持 map 值中的空格及非 ASCII 字符。
- 未知变量、非法名称、缺失内置目录、空自定义值、内置变量覆盖和格式错误标记均返回错误。
- 检查所有路径字段的展开行为，以及展开后绝对路径、相对路径、候选优先级和缺失目标行为仍符合现有契约。
- 检查 `processrunner` 展开 `XDG_CONFIG_HOME: "${APP_DIR}/third"` 等环境值，未知变量时不启动子进程，且普通环境变量键和值行为不变。
- 在 Windows、Linux、macOS 原生 CI 环境运行包测试；另可在 WSL 验证 Linux 部署场景。
